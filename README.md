## 📌 1. 프로젝트 소개

본 프로젝트는 Claude Code CLI를 이용해 **조선소 통합관리 시스템(SWP Shipyard)**을 구현하면서, AI 기반 개발 과정의 토큰 사용량을 줄이기 위한 워크플로를 비교·분석하는 실험입니다.

기존 Ver1에서는 기능 명세 기반 개발과 단계별 컨텍스트 로딩을 적용하여 큰 폭의 토큰 감소를 기록했습니다.

Ver2에서는 이를 더욱 개선하기 위해 멀티 세션 관리와 개발 자동화를 도입했습니다.

그러나 실제 측정 결과, **Ver1 대비 총 토큰 사용량이 약 87% 증가**했습니다.

이번 실험에서는 이러한 결과가 발생한 원인을 분석하고, 다음 버전에서 개선할 방안을 도출했습니다.

### 🔗 프로젝트 버전

| 버전 | 프로젝트 | 주요 실험 |
|---|---|---|
| Ver1 | [shipyard-TokenOptimization](https://github.com/Jihoons-Growthlab/shipyard-TokenOptimization) | 명세 기반 개발, 단일 세션, 단계별 컨텍스트 최적화 |
| **Ver2** | [shipyard-TokenOptimization-ver2](https://github.com/Jihoons-Growthlab/shipyard-TokenOptimization-ver2) | 멀티 세션, `/build`, Ponytail, 자동화된 검증 |
| Ver3 | 개선 실험 준비 | API 호출 최소화, 로컬 스크립트 자동화, 세션 관리 개선 |

## 🎯 2. Ver2 개발 목표

Ver1은 한 세션에서 단계별 명세를 읽으며 개발을 진행했습니다.

Ver2에서는 단일 세션에 개발 이력이 누적되는 문제를 개선하기 위해 다음 전략을 적용했습니다.

| 최적화 전략 | 목적 |
|---|---|
| 멀티 세션 분리 | 작업 단위별 컨텍스트 누적 방지 |
| `/build` Skill | 개발 절차 자동화 및 반복 프롬프트 최소화 |
| Ponytail 활용 | AI 개발 과정의 도구 사용 및 작업 흐름 개선 실험 |
| `PROGRESS.md` | 세션 간 개발 진행 상황 공유 |
| Playwright MCP | UI 검증 및 화면 비교 자동화 |
| 토큰 사용량 추출 | API 호출·캐시·출력 토큰 분석 |

핵심 가설은 다음과 같았습니다.

**"작업을 독립된 세션으로 분리하고 자동화된 개발 워크플로를 적용하면 전체 컨텍스트 처리량과 토큰 사용량이 감소할 것이다."**

## 🔄 4. Ver1과 Ver2의 바이브 코딩 방식

### Ver1 — 명세 기반 단일 세션 개발

```text
기능 명세 작성
      ↓
/rebuild 실행
      ↓
단계별 명세 로딩
      ↓
기능 구현
      ↓
검증 및 진행 상태 기록
      ↓
다음 단계 진행
```

**주요 특징**

- 하나의 개발 세션에서 작업 수행
- 정해진 명세와 작업 순서에 따라 구현
- 필요한 시점에 해당 기능 명세 로딩
- `PROGRESS.md`를 이용한 진행 상태 관리
- 불필요한 MCP 및 중복 문서 축소

Ver1에서는 초기 개발 방식 대비 총 토큰 사용량을 약 67.6% 줄인 결과를 기록했습니다.

### Ver2 — 멀티 세션 기반 자동화 개발

```text
/build 실행
      ↓
작업 및 세션 상태 확인
      ↓
세션별 개발 작업 수행
      ↓
명세 및 기존 코드 분석
      ↓
기능 구현
      ↓
테스트 및 Playwright 검증
      ↓
PROGRESS.md 기록
      ↓
다음 세션 진행
```

**주요 변경 사항**

- 단일 세션 대신 여러 세션으로 작업 분리
- `/build` 중심의 개발 워크플로 구성
- 세션별 작업 범위 및 상태 관리
- Playwright를 통한 반복 화면 검증
- Ponytail을 포함한 개발 도구 구성 실험

세션별 컨텍스트 크기를 줄이는 데 초점을 맞추었으나, 실제 실행에서는 API 호출 횟수가 크게 증가했습니다.

## 📊 5. 토큰 사용량 비교 결과

### 5.1 Ver1 vs Ver2

두 프로젝트의 Claude Code 사용 기록을 기준으로 비교했습니다.

| 측정 항목 | Ver1 | Ver2 | 변화 |
|---|---:|---:|---:|
| **총 토큰 사용량** | **20,995,581** | **39,270,601** | **+87.0%** |
| API 호출 횟수 | 63 | 276 | +338.1% |
| 세션 수 | 1 | 6 | +5개 |
| 입력 토큰 | 130 | 564 | 증가 |
| 출력 토큰 | 281,057 | 380,829 | +35.5% |
| 캐시 생성 토큰 | 474,177 | 913,747 | +92.7% |
| 캐시 읽기 토큰 | 20,240,217 | 37,975,461 | +87.6% |
| 호출당 평균 전체 토큰 | 약 333K | 약 142K | -57.3% |

### 5.2 결과 분석

**개별 호출의 처리량은 줄었지만, 호출 횟수 증가로 총 사용량은 오히려 증가했습니다.**

```text
Ver1
API 호출: 63회
총 토큰: 약 2,100만

Ver2
API 호출: 276회
총 토큰: 약 3,927만

결과
호출당 평균 토큰 ↓ 57.3%
전체 호출 횟수 ↑ 338.1%
총 토큰 사용량 ↑ 87.0%
```

이 결과는 세션 분리만으로 전체 토큰을 최적화할 수 없다는 점을 보여줍니다.

특히 컨텍스트를 줄이더라도, 적은 작업을 수행하기 위해 API를 반복 호출한다면 전체 사용량이 증가할 수 있습니다.

> **주의:** 총 토큰에는 캐시 읽기·생성 토큰이 포함되어 있습니다. 총 토큰 증가율은 실제 청구 비용 증가율과 같지 않으며, 두 버전의 구현·검증 범위 차이를 통제한 실험도 아닙니다.

## 🔍 6. 토큰 사용량 증가 원인 분석

Claude Code 세션 로그를 분석한 결과, 다음과 같은 비효율을 확인했습니다.

### ① 지나치게 많은 짧은 API 응답

가장 큰 원인으로 확인된 것은 작은 작업마다 API 호출이 반복된 점입니다.

| 항목 | 분석 결과 |
|---|---|
| 출력 700토큰 미만 응답 | 173회 |
| 전체 호출 중 비중 | 약 63% |
| 해당 호출의 총 처리 토큰 | 약 23.2M |

예를 들어 다음과 같은 작업이 각각 별도의 호출에서 진행되었습니다.

```text
파일 검색
   ↓
파일 확인
   ↓
코드 한 부분 수정
   ↓
결과 확인
   ↓
추가 수정
   ↓
재검증
```

이 과정에서 이미 누적된 컨텍스트가 반복적으로 처리되었습니다.

**개선 방향:** 관련 파일 탐색과 수정 작업을 하나의 작업 단위로 묶고, 반복적인 단순 명령은 로컬 스크립트로 처리합니다.

### ② 세션 간 컨텍스트 재사용 문제

S5와 S6에서 동일한 세션 ID가 재사용된 기록을 확인했습니다.

그 결과 S6이 새로운 컨텍스트에서 시작되지 않았으며, 분석상 약 3.5M 토큰의 추가 컨텍스트 처리량이 발생한 것으로 추정되었습니다.

**개선 방향:** 세션 시작 시 ID를 검사하고, 완료된 세션의 재사용을 방지하는 검증 로직을 도입합니다.

### ③ Playwright 기반 화면 검증 반복

Ver2에서는 Playwright MCP를 사용해 UI 검증을 진행했습니다.

| 항목 | Ver1 | Ver2 |
|---|---:|---:|
| Playwright 주요 브라우저 실행 호출 | 27회 | 50회 |

일부 구간에서는 다음 작업이 30회 이상 반복되었습니다.

```text
화면 캡처
   ↓
이미지 확인
   ↓
CSS 수정
   ↓
화면 재캡처
   ↓
다시 비교
```

UI 품질 확인에는 도움이 되었으나, 화면 확인 과정에서 API 호출과 컨텍스트 처리량이 크게 증가했습니다.

**개선 방향:** 화면을 일괄 캡처하고, 자동 비교 결과에서 차이가 큰 화면만 AI가 확인하도록 변경합니다.

### ④ 세션별 중복 소스 탐색

세션이 분리되면서 다른 세션에서 확인했던 소스코드를 다시 탐색하는 문제가 발생했습니다.

특히 Vue 컴포넌트와 CSS 구조를 반복적으로 확인했습니다.

**개선 방향:** 소스맵을 자동 생성하고, 변경된 파일에 대해서만 갱신하여 세션 간 재탐색을 최소화합니다.

### ⑤ 기본 컨텍스트 로딩 비용

Ver2 분석에서 세션 초기 컨텍스트는 약 44K 토큰 수준이었습니다.

이러한 고정 컨텍스트는 호출 횟수가 증가할수록 누적 처리량에 영향을 줍니다.

**개선 방향:** 불필요한 MCP, Plugins, 공통 지침과 설정을 점검하고 필요한 기능만 로딩하도록 개선합니다.

단, 고정 컨텍스트의 세부 구성과 각 설정이 차지하는 토큰은 추가 측정이 필요합니다.

## 🧠 7. 이번 실험에서 얻은 교훈

### 세션 분리는 최적화의 수단이지 목표가 아니다

세션을 분리하면 호출당 컨텍스트를 줄일 수 있지만, 각 세션의 준비·탐색·검증이 반복되면 전체 토큰 사용량이 증가할 수 있습니다.

### API 호출당 수행하는 작업의 밀도가 중요하다

작은 파일 확인이나 간단한 명령을 위해 AI를 반복 호출하는 방식은 비효율적일 수 있습니다.

관련 작업을 적절히 묶고, 단순하고 결정적인 작업은 코드로 자동화할 필요가 있습니다.

### 검증 자동화에도 비용이 발생한다

Playwright를 활용한 UI 검증 자체가 문제가 아니라, AI가 화면을 반복적으로 확인하고 작은 수정을 여러 차례 수행한 과정이 문제였습니다.

검증 기준과 실행 횟수를 명확하게 정해야 합니다.

### 최적화는 실제 수치로 판단해야 한다

멀티 세션, Skill, Plugins 등은 유용한 기능이지만, 기능을 많이 도입했다고 토큰 효율이 반드시 높아지지는 않습니다.

실제 API 호출 수와 컨텍스트 처리량을 측정하고 검증하는 과정이 중요합니다.

## 🚀 8. Ver3 개선 계획

Ver2 분석 결과를 토대로 다음 실험에서는 **API 호출 최소화와 로컬 자동화 중심의 워크플로**를 적용할 계획입니다.

### 목표

- 동일한 필수 기능 명세를 기준으로 재구현
- AI의 단순 반복 작업 최소화
- 불필요한 세션 재사용 방지
- 반복적인 화면 확인 감소
- 전체 토큰 사용량 10M 이하를 공격적인 실험 목표로 설정

10M은 실측 절감 예상치가 아니라 실험 목표입니다.

### Ver3 개발 방식

```text
       명세 및 참고 자료
                │
                ▼
       로컬 작업 상태 분석
                │
                ▼
      필요한 개발 단계 선택
                │
                ▼
       최소 컨텍스트 로딩
                │
                ▼
         기능 단위 구현
                │
                ▼
       로컬 자동 검증 실행
                │
                ▼
       실패 항목만 AI 분석
                │
                ▼
       간결한 인수인계 기록
                │
                ▼
          다음 단계 진행
```

### 개선 항목

| 개선 대상 | Ver2 | Ver3 계획 |
|---|---|---|
| 세션 관리 | 세션 중복 재사용 발생 | 세션 ID 검증 및 단계별 새 세션 |
| 코드 탐색 | 반복적인 Read/Bash | 소스맵 생성 및 재사용 |
| 기능 구현 | 짧은 수정·확인 반복 | 관련 작업 일괄 처리 |
| 테스트 | AI가 반복 실행 | 로컬 검증 스크립트 중심 |
| UI 검증 | Playwright MCP 반복 호출 | 일괄 캡처 및 차이 기반 확인 |

## 💡 10. 향후 확장 방향

이번 실험에서 확인한 문제는 특정 조선소 프로젝트에만 해당하지 않습니다.

Claude Code를 사용하는 다양한 개발 환경에서도 반복적인 컨텍스트 로딩, 세션 관리, 검증 호출 등이 발생할 수 있습니다.

향후에는 이러한 최적화 방식을 일반화하여 다음과 같은 도구로 확장하는 것을 목표로 합니다.

**AI 기반 Claude Code 개발환경 최적화 도구**

- 프로젝트 구조 및 기술 스택 자동 분석
- 최적화된 `CLAUDE.md`, Rules, Skills 생성
- 사용자 친화적인 GUI 환경 구성
- `/build` 등 사용자 정의 명령 실행 지원
- 세션 상태 및 토큰 사용량 분석
- 반복 작업과 불필요한 컨텍스트 자동 감지
- 프로젝트별 최적화 전략 추천

궁극적으로 개발자가 Claude Code의 내부 설정을 모두 이해하지 않더라도, **프로젝트에 적합한 AI 개발환경을 쉽게 구성하고 관리할 수 있도록 하는 것**이 목표입니다.
